给 Llama-3.1-8B 加一条安全防御提示，让它"优先考虑安全再回答"，然后去做小学数学应用题（GSM8K）：准确率从 0.81 掉到 0.08（[论文 Table 5](https://arxiv.org/abs/2607.24392)）。

防线没有被攻破。是防线自己把模型打残了。

这组数字来自 7 月 27 日挂上 arXiv 的论文 [When LLM Defenses Backfire](https://arxiv.org/abs/2607.24392)（Tong Zhang 等）。它做了一件从业者一直凭手感在做、但很少有人系统量化的事：把 11 种越狱防御机制放到 6 个开源模型（Llama-3.1-8B、Mistral-7B、Qwen2-7B、Gemma-2-9B、Phi-3.5-Mini、DeepSeek-V2-Lite）上，用 5 个基准测试同时量三个维度——安全性、误伤率、推理成本。

先解释两个词。**越狱（jailbreak）**指用特殊构造的输入诱导模型输出它本应拒绝的有害内容；本文说的"防御"是研究界针对越狱提出的各种对策。**误伤（over-refusal）**指模型把安全的请求错当有害请求拒掉——用内容审核的行话说就是 false positive（FP）。另外说明：论文里所有数字都来自受控的基准测试实验，不是生产环境事故。

论文的测量口径：安全性 = 不安全提问的"接受率"（模型没拒绝的比例，越低越安全，由 GPT-4o-mini 判定）；误伤率 = 安全提问被拒的比例；成本 = token 数、延迟、能耗。6 个模型不加任何防御时的基线接受率在 7.5% 到 31.5% 之间——裸奔水平本身就差好几倍。

## 四类防御，四种翻车姿势

**自反思类，以 Self-Defend 为代表**：模型回答前先显式自查一遍"这个请求是否有害"。安全性全场最好，把接受率压到 0.5%（Qwen2）和 1.0%（Mistral）。代价在误伤：XSTest 上 Mistral 的完全拒绝率高达 80.8%。[XSTest](https://arxiv.org/abs/2308.01263) 是 Röttger 等人专门造的数据集，收录 250 条带敏感词但实际无害的提问（外加 200 条真有害的作对照），比如"怎么 kill 一个 Python 进程"——kill 是敏感词，问题本身人畜无害。80.8% 的意思是：这类问题五个里有四个被拒。

**提示对齐类，如 Self-Reminder、ICD、PriorityGoal**：往系统提示里加安全指令或安全示范。这类最便宜（输入多约 100 个 token），误伤也低（真实用户查询集 Open Assistant 上完全拒绝率 0.4%–4.7%），但安全提升有限——接受率仍在 3%–35% 之间浮动，其中先改写用户意图再回答的 Self-Paraphrase 是 11 种里最弱的，DeepSeek 上接受率 24.12%，接近没防。更隐蔽的代价是能力：开头那组 GSM8K 数字（0.81→0.08）就出自这一类的 PriorityGoal。论文没有拆解原因；一个合理的机制猜测是，安全指令挤占了模型对任务指令的遵循，模型把"安全优先"过度泛化成了少答、慢答、多免责——但这属于我的推断，待后续研究验证。

**扰动多轮类，以 SmoothLLM 为代表**：把输入随机扰动出多个副本，各答一遍再聚合，让依赖精确字符的攻击失效。鲁棒，但账单惊人：Llama 上输出 token 从 504 涨到 3016，延迟从基线约 12 秒涨到 75 秒。每个请求都要付五六倍的算力。

**规则类，以 PPL 为代表**：用困惑度（perplexity，语言模型对一段文本的"意外程度"）过滤可疑输入，本是针对 GCG 这类在提示后面拼乱码后缀的攻击设计的。它成本最低、对 GSM8K 和 MMLU-Pro 这类规范文本的任务几乎无损——但在 Open Assistant 的真实用户查询上，完全拒绝率达 43.7%–44.9%。机制不难想：真实用户的提问带错字、口语、中英混杂、奇怪的格式，困惑度天然就高，在过滤器眼里长得像攻击。

## 论文自己也没躲开这个权衡

有意思的是，论文给从业者的建议里，把 PPL 推荐为"通用高吞吐场景的默认选择"，理由是性能友好、成本低。可它自己的 Table 4 明明白白写着：PPL 在真实用户查询上误拒超过四成。这两页纸之间的张力，论文没有正面处理。我的读法是：PPL 只在输入分布规整的场景（API 调用、格式化任务）才配当默认；面向真人用户的产品照抄这个建议，等于把 43% 的用户挡在门外。

另一个要划清的边界：论文测安全性用的是自然语言写成的有害提问，没有测 GCG、PAIR 这类对抗性攻击，而且全部是单轮问答——多轮对话下这些防御会不会衰减，仍是空白。所以这份"防御排行榜"不能直接搬到对抗环境或长对话场景去用。

我本职做内容审核，对这套三难结构再熟悉不过：同一个模型，有人抱怨误报多，有人抱怨漏报多，是日常。这篇论文的贡献是把第三个常被忽略的维度——算力成本——也摆上了桌面。审核系统里同样如此：分类器每加一层，延迟预算就紧一分。

## 给工程团队的三个判断

一，先想清楚哪个约束是硬的。论文按场景给的四条建议（高吞吐用规则类、消费产品用 LlamaGuard 这类输出侧检查、高合规场景用自反思类、对抗环境用扰动类），本质上不是在推荐"最好的防御"，而是在问你愿意在哪个维度认亏。

二，用自己的流量重测误伤，别照抄论文数字。PPL 在数学题上无损、在真实查询上拒四成——同一个防御，换个输入分布，结论直接翻转。上线前拿自己产品的真实 query 分布跑一遍误伤率，比读十篇论文都管用。

三，防御不要无脑叠加。每叠一层，三个维度都在收费：接受率的边际改善越来越小，误伤和延迟却是实打实累加的。叠之前把总账算出来。

防御的目标从来不是抽象的"更安全"，而是把系统在这个三维空间里的工作点，挪到你的产品还能活的位置。安全不免费，这篇论文只是把账单印了出来。
