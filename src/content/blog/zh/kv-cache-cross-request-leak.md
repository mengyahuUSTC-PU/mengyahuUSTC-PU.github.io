把不想公开的内容交给托管模型时，我通常担心两件事：会不会被拿去训练，日志会存多久。这两件事都写在服务条款里，可以逐条去问。

还有第三种可能，条款里一般不会写：我的提示词还留在推理服务器的显存里，下一个请求读到了它。

10 月 26 日，Cloudflare 披露的就是这种情况（[原文](https://blog.cloudflare.com/kv-cache-exposure-remediation/)）。Workers AI 上的 GLM-5.3 从 8 月 27 日上线到 9 月 9 日修复，有 155 条响应带出了其他客户在此前不久发给同一模型的内容，包括提示词和生成到一半的回答。这 155 条全部来自超过 681,280 token 的长提示词请求。Cloudflare 说受影响客户"数量很少"，没有给出具体数字，也没找到蓄意利用的证据。

## 先说 KV cache 是什么

模型读提示词时，每读一个 token 都会算出一组中间结果。后面生成回答时要反复回看这些结果，所以服务器把它们存在显存里，这就是 KV cache。可以把它理解成模型做题时的草稿纸，提示词有多长，草稿就写多长。

显存很贵，推理引擎会把它切成固定大小的"页"，请求来了分几页，用完收回再分给下一个请求。Cloudflare 在文中说明，这些页在两次请求之间**不清零**，新请求只覆盖自己写到的部分。这是业界为了性能常见的做法，代价是安全性完全依赖一件事：引擎必须准确记住每一页现在属于谁、哪些已经写过。

## 漏洞怎么发生的

Workers AI 用开源引擎 SGLang 跑模型，部署方式是 prefill 和 decode 分开：一组 GPU 负责读完提示词、写出草稿页（prefill），再通过高速网络把这些页传给另一组 GPU 逐字生成回答（decode）。

问题由两件事叠在一起造成。

第一是配置不匹配。GLM-5.3 对外宣称支持 1,048,576 token 的上下文，但 prefill 节点上的 KV 池只装得下 681,280 token。SGLang 启动时按加载完权重后剩下的显存决定池子大小，不会强制它和宣称的上下文长度一致。Cloudflare 上线前就知道这个差距，长上下文测试也跑过，但测试只看了 HTTP 状态码和性能，没检查输出内容对不对。

第二是 SGLang 的 bug。提示词超出池子容量时，调度器会把请求标记为"拒绝"，并把提示词换成一个 1 token 的占位符。单机部署下，这样处理会正常返回错误。可在分离部署里，准入队列检查的是请求有没有"完成"，没看它是否被"拒绝"。被拒的请求看起来还活着，于是 prefill 对占位符跑了一遍，只写了一页就宣告完成。decode 那边已经按原始提示词长度预留了页数。按 Cloudflare 举的例子，预留了 8 页，只有第 1 页是这个请求自己写的，剩下 7 页还是前面别人请求留下的草稿。模型照常读完这 8 页，生成了一段通顺的回答。

客户端收到的是 HTTP 200，返回的 prompt token 数也和长提示词对得上。从调用方看，一切正常。

这里要分清方向。拿到别人数据的是发送超长提示词的那一方；数据被泄露的，按机制推断，可能是任何在此前不久用过这个模型的客户，和对方的提示词长短无关。Cloudflare 的说法是"此前不久发给同一模型的请求"，没有进一步限定受害方的范围。

## 上游早就有人报过

这个 bug 有前史。7 月 6 日，SGLang 仓库已经有用户提交了 [issue #30233](https://github.com/sgl-project/sglang/issues/30233)，在 GLM-5.2 上复现了同样的现象：超长输入被中止后，decode 读着没初始化的缓存生成"无关输出"。报告人把它当成输出乱码的稳定性问题，并附上了补丁思路。对应的修复 [PR #30551](https://github.com/sgl-project/sglang/pull/30551) 7 月 8 日提交，我查看时仍未合并。issue 本身在 9 月 5 日被 GitHub Actions 机器人以"长期无活动"自动关闭。三天后，安全研究员 Gadi Evron（Knostic）通过 HackerOne 向 Cloudflare 报告了这个漏洞。

同一个现象，在 issue 里被描述成"输出乱码"，在安全报告里被描述成"读到别人的会话"。区别在于那几页"未初始化"的缓存里实际装着什么。在多租户服务里，那里装的就是其他客户的数据。

Cloudflare 的响应很快。按其时间线（UTC），9 月 8 日 23:11 收到报告，9 月 9 日 14:00 把模型下线，19:40 恢复上线，前后约 20 小时。修复包括把 KV 池扩到约 204 万 token，让合法请求永远走不到拒绝分支；同时给引擎打补丁，让被拒请求在分配页、传输缓存之前就带着原错误退出，decode 端还会核对实际收到的 token 数是否等于预留数。相关修复已进入 SGLang v0.5.22。

## 这和之前研究的缓存泄露不是一回事

学术界讨论推理缓存的隐私风险已有一段时间，焦点主要是"前缀缓存"的时序侧信道：如果服务商让不同用户共享相同前缀的缓存，攻击者可以通过响应快慢判断某段文字是否被别人发过，再逐 token 猜出内容（[arXiv:2409.20002](https://arxiv.org/abs/2409.20002)）。斯坦福团队对商用 API 做了审计，发现包括 OpenAI 在内的 7 家提供商存在跨用户的全局缓存共享（[arXiv:2502.07776](https://arxiv.org/abs/2502.07776)）。

那类风险来自有意设计的共享，攻击者需要反复测时间、慢慢推断。Cloudflare 这次的情况不同：服务方并没有打算共享任何缓存，是错误处理分支上的一个状态判断写错了，别人的原始内容就直接进了你的上下文。不需要测时间，也不需要攻击者，正常用户发一个长提示词就能触发。

## 用托管模型的 builder 该问什么

作为普通用户，能做的不多：155 条响应、只在超长提示词下触发，绝对风险不高。但机制说明，显存复用不清零是推理服务的常见默认，同类 bug 在任何引擎、任何服务商都可能出现。

对接托管推理服务时，我会追问几件具体的事：

- 显存页在交给下一个请求前是否清零，或者读取时是否校验归属。Cloudflare 自己说下一步要做的就是"每页打标签、读取时检查"。
- 对外宣称的上下文长度和每个节点实际的 KV 池容量，上线前有没有自动比对。
- 长上下文测试有没有检查输出内容，比如在请求里埋入标记串，检查它会不会出现在别的请求里。Cloudflare 修复后用的就是这种金丝雀测试。
- 用的是哪个推理引擎、哪个版本，上游安全修复多久能跟进。
- 是否默认开启跨租户的前缀缓存，能否关闭。
- 发生跨租户泄露时，是否会通知受影响的客户。Cloudflare 这篇披露里没有提到是否联系了受影响客户。

最后这个问题我最想要答案。这次的 155 条响应里，有人收到了别人的数据，也有人的数据被别人收到。前者至少看到了一段奇怪的回答，后者可能至今都不知道。
