先把这套设计讲清楚，不然后面的攻击看不明白。

现在的推理模型（reasoning model）在给你最终答案之前，会先生成一大段"想的过程"，也就是思维链（chain-of-thought，CoT）。这段过程厂商不想让你直接看到，理由有两个：一是怕被拿去蒸馏（distillation，指用强模型的输出当训练数据，喂给自己的弱模型让它学会同样的推理），二是这段思路里可能夹带不该外泄的内容。可推理模型又要支持多轮对话，下一轮得接着上一轮的思路往下走。厂商的解法是：不在自己服务器上留这段思维链，而是把它加密成一段密文块，随响应一起发回给你的客户端；你下一次请求时，把这段密文原样带回去，服务器解开、接着算。整个服务因此是"无状态"的（stateless，服务器不为你保存任何会话数据），状态被推到了你手里。

听起来很干净。问题只有一个：这段密文块，到底绑定了谁？

8 月 10 日挂上 arXiv 的一篇论文给出的答案是——谁都没绑定（[arXiv:2608.09867](https://arxiv.org/abs/2608.09867)，作者为 Alexander Panfilov、Ilia Shumailov、Jonas Geiping、Maksym Andriushchenko 等）。作者发现，这些加密块在同一家厂商的生态里"跨会话、跨用户、跨模型完全通用、可以互换"。也就是说，加密和解密的能力，并没有跟发出它的那次会话、那个账号、那个具体模型捆在一起。密文换个地方照样解得开。

这一条看似技术细节，却是整条攻击链的命门。

## 攻击方从不去碰强模型

拿到这个事实，攻击方设计了一个漂亮到有点讽刺的动作：他们根本不去攻破那个生成了敏感推理的强模型，而是把强模型吐出的加密块，直接喂给同一家厂商旗下一个更弱、防护更松的小模型，然后让小模型"把这段加密推理原样抄成明文"。

因为密文没绑定模型，服务器在处理小模型这次请求时，照样把它透明地解开，小模型拿到的是一段明文推理，当成正常上下文；你再让它逐字复述，它就复述了。全程强模型的安全护栏一次都没被触发——你压根没跟强模型说过话。那个弱模型在这里的角色，等于一台"解密预言机"（decryption oracle，一个你能反复投喂密文、它就替你吐出明文的部件）。

论文把这套手法能干的事拆成四类，每一类的后果性质都不一样：

**一是绕过反蒸馏。** 厂商加密思维链的初衷之一就是不让人偷走推理过程去训练竞品，可这套解密重放直接把初衷架空了：想要多少条强模型的完整推理轨迹，就能解出多少条。

**二是大规模扒隐私。** 很多人会把带 agent 日志的运行记录传到公开仓库，日志里就含这些加密推理块。作者从公开仓库抓来的 315,320 个推理块里，还原出 367 条个人身份信息（PII）和 182 条凭据（credential，含 API 密钥、口令这类）。关键在于，这些东西在可见的对话正文里是看不到的——它们只藏在那段"加密"推理里，机主以为传出去的是加了密的黑箱，实际等于明文。

**三是掏出被拦在明面之外的危险信息。** 模型的安全过滤通常作用在最终回答上：你问一个危险问题，它拒绝回答。但拒绝的是"输出"，它在思维链里可能已经把步骤想了个七七八八。把这段推理解出来，就拿到了那份"最终答案里被删掉、推理过程里却还在"的内容。

**四是隐形提示注入（prompt injection）。** 反过来用：攻击者把恶意指令塞进一段加密块里，让它在系统看来像是模型自己的推理。用在 agent 流水线上，这段"伪装成模型自省"的载荷可以悄悄操纵后续行为，且很难被察觉，因为它顶着"模型内部思考"的身份。作者提到这可以用来污染公开流传的 agentic 运行记录。

这四条覆盖了 Anthropic、OpenAI、Google 三家（这也是目前用加密块方式保护思维链的主要厂商）。据论文披露，这不是凭空冒出来的新问题：更早就有研究者指出加密块能被移出原始上下文重放，但被厂商当作"没有安全影响"驳回过——具体是谁、何时、厂商原话如何，我没能在论文正文（站点与 PDF 都返回 403）里核到，只在二手报道里见到，暂不当作实锤写入。

## 问题不在密码学，在"绑定"

值得说清的是，这里被攻破的不是加密算法本身。密文没被暴力破解，签名校验也在起作用（改动密文会被服务器拒绝）。出事的是**绑定关系**：一段密文能不能解开，本该取决于"是不是原来那个用户、那次会话、那个模型在用它"，而现在只取决于"它是不是一段合法密文"。合法就解，不问出处。

这正是"无状态"设计埋下的代价。为了不在服务器上留数据（这本身是很多企业看重的零数据留存承诺的技术基础），厂商把会话状态外包给了客户端。可一旦交出去的这份状态没有和持有者做密码学绑定，它就是可携带的；可携带，就意味着可重放。加密在这里只解决了"路上不被看到"，没解决"换个人拿着还能不能用"。这两件事常被混为一谈，这篇论文把它们的区别摆到了台面上。

## 调商业 API 的人该改哪几个假设

如果你在用这些厂商的推理 API 搭产品，有几条假设需要当场改掉：

- **别把"加密的思维链"当成一道安全边界。** 它不是保险箱，更接近"暂时没人念出来的明文"。凡是你不希望第三方读到的东西，就不要默许它流进 prompt、指望思维链替你藏住。你在界面上看到模型"拒绝了"，也不代表它没在推理里把该拒绝的内容想完整。
- **把推理块当敏感数据来对待日志。** 往公开仓库、gist、帖子里传运行记录前，先把 reasoning 字段里的密文块删掉；那 182 条凭据就是这么泄的。若某次会话的推理已被解出来过，牵涉到的密钥该轮换就轮换。
- **agent 系统要过滤外来的"推理块"。** 既然一段加密块能伪装成模型自己的思考被注入，凡是来自用户或外部的内容，进 API 调用前都要清洗，别让攻击者塞进来的块顶着"内部推理"的身份被信任。

据论文披露，三家厂商在收到通报后都部署了服务端缓解，最初那套跨模型重放的验证代码在当前 API 上已复现不出来。这算是好消息，但别把它读成"警报解除"。真正的教训不在这一个被补上的洞，而在那句被架空的默认假设：把状态推给客户端省了存储，却省不掉给状态上锁的责任；只要绑定这一步偷懒，加密做得再规整，也拦不住换个人、换个模型把它重放一遍。
