## 交稿纪律

- frontmatter 的 title 和 description 一律用双引号包裹（英文冒号会炸 YAML，导致整站构建失败）（2026-07-19，快讯英文版标题含冒号导致部署挂掉）

- **绝不留 TODO/FIXME/待补注释交稿**。能当场验证的当场验证；确实无法验证的，并入「事实核查点」清单并写明验证指向。交稿前整体通读一遍，专查未完成项（2026-07-19，用户在 PR #6 抓到遗留 TODO）
- 用户的提问式反馈("这里是不是有问题？""有没有没做完的？")一律当作行动请求处理：查证并修复，而不是回答「是的有」或原样返回
- 描述 AI 安全「事故/事件」时必须核实其性质：是真实生产环境中发生的部署事故，还是厂商/研究者专门设计的红队测试或评估实验，两者不可混为一谈；正文需明确注明信息来源及事件性质，无法确认是真实事故时不得称其为"事故"（2026-07-21，用户质疑 OpenAI 相关案例是否为真实部署事故而非专门测试）
- 文中提及安全机制/防护效果（如分类器、检测手段）时，需核实是否有对应场景的 benchmark 或研究支撑，尤其注意区分单轮（text in, label out 式分类器）与多轮对话（multiturn）、长对话（long conversation）场景——现有安全研究多为单轮，若声称的机制针对多轮/长对话场景却找不到对应研究，须在正文注明这一研究空白，不能默认已有研究覆盖（2026-07-21，用户追问文中三个机制是否有对应 multiturn / long conversation 的 benchmark 和研究）
- 引用研究支撑某个机制/论断时，须核实该研究实际测量的构念（construct）与论断的性质一致——如论断是"安全约束力衰减"，就不能引用测的是"任务执行成功率"（能力，capability）的论文；引用前先确认原论文测的到底是能力还是安全行为（如 jailbreak 成功率、有害内容生成率），构念不匹配则换成真正测安全行为的研究（2026-07-21，用户指出"约束力随轨迹长度衰减"引用的论文实际测的是任务成功率而非安全指标）
- 文中对事件/做法使用"罕见""首次"等程度或频率判断词，或提出自造的概念/框架/指标（如某个"系数"）暗示其新颖性时，须能给出可验证的依据——横向对比同类案例、检索相关领域是否已有对应的成熟研究方向（如声称的"系数"类论点需先查是否已有 user intention/intent inference 等研究）；若已有相关研究，须在正文明确说清新提出的东西与既有研究的关系及具体新意所在，不得绕开已有文献自称首创；无法证实则删除该修饰词或改写为客观中性表述，不得凭直觉扣上此类修饰语（2026-07-21，用户质疑 title/description 中"罕见公开"一词的依据；2026-07-25，用户追问"精灵系数"一文是否已有 user intention 相关研究、该系数新意何在）
- 文中声称某种做法（如"买实体书扫描用于训练"）具备合法性/可复制性时，必须核实其适用范围——是仅针对本案涉事公司、涉事内容类型（如纸质书）成立，还是可泛化为所有 AI 公司、所有版权内容类型（如电影、音视频）都适用的通用规则；原始判决/来源未明确回答这一范围时，须在正文注明这是尚未确认/存在争议的推论，不能让读者误以为已是普遍适用的合法路径（2026-07-21，用户追问"买书扫描训练合法"这条路径是否对所有科技公司、所有版权内容类型（书、电影的 image/video/audio）都成立）
- 针对 inline comment 逐条修改后，正文容易残留"回答式"语气（像是在回复审阅者的提问，而非自然的文章叙述）；逐条改完后必须整体通读一遍，把这类问答腔改写为正常叙事语气，同时检查全文行文是否顺畅、故事结构是否完整，不能只满足单条评论的字面要求（2026-07-21，用户反馈多轮 inline comment 修改后正文有回答问题的口气，要求整体 polish 一遍）

## 信息源

- 不收录标题党/二手聚合类媒体（量子位曾加入即被移除，2026-07-19）；中国公司动态走官方渠道（Kimi/DeepSeek 官方页）+ HN/TechCrunch，宁缺毋滥

## 语言与表达

- 避免"AI 味"过重的空洞升华式短语，**「能带走什么/能带走的判断」一词全面禁用**——这是英文 "takeaway" 的直译，中文里非常别扭；总结段标题改用「核心启示」「关键结论」或结合内容的具体说法（如「给从业者的三个判断」）（2026-07-19 首次反馈；2026-07-24 用户再次点名该词并要求全站替换，已重复出现两次，视为硬禁）
- 不要植入缺乏普遍共识支持的价值判断/因果论断（如"开源模型更安全"），若无充分论据支撑应直接删除而非武断断言；文中提出"把审核/判定从某一层移到另一层"一类替代方案（如把内容层的分类器审核换成身份验证/个人资质认证）时，须验证新方案是否真正解决了原问题，而不是把同一个核心难题（如"如何判断一个人有无恶意"）原样搬到新的层级；同时须如实评估该方案带来的新增审核成本/工作量，不能把只是转移问题的方案包装成已解决的答案；讨论内容审核/分类类系统（尤其是色情、暴力等判定边界主观的内容，而非 object detection 这类边界清晰的任务）时，须承认中间地带存在标注者间分歧、FP/FN 权衡、"谁在提问"（如安全研究者出于正当目的做 red teaming）等文本本身无法判断的语境因素，以及不同用户群体接受度不同导致一套 universal moderation 标准无法满足所有人；若全文给不出能化解这一结构性矛盾的答案，须在结论处如实承认这是难以完全解决的本质问题，不能给出假的"已解决"式收尾（2026-07-19，用户指出"开源的更安全"缺乏依据；2026-07-26，用户指出把授权判定移到身份验证/个人资质认证一段忽略了如何界定恶意意图的基准问题及由此产生的巨大审核难度；2026-07-26，用户以性内容审核为例指出标注分歧、FP/FN、语境依赖等属本质问题，追问文章结论是否只是回避了这一点）
- 文中引入专业/抽象术语或概念（如"指令冲突""胁迫场景""勒索率""零日（zero-day，指尚未公开、厂商未修复的漏洞）"、标题里提到的"猜想"等）时必须在正文顺带给出简明解释，不能预设读者已理解，也不能让标题提了而正文不展开；此问题已反复出现，交稿前需专门自查一遍全文术语是否都已在首次出现处解释清楚（2026-07-21，用户先后三次反馈：「指令冲突」看不懂、标题所说的猜想需要在文中解释、Claude 案例中的「胁迫场景」「勒索率」未解释；2026-07-25，用户看不懂"代理软件的零日"中「零日」何意）
- 文中使用跨行业类比/引用来支撑论点（如"航空业靠事故报告改进安全"这类类比）时，必须在正文交代该类比/引用的具体内容、来源，以及它与本文论点的对应逻辑，不能一笔带过让读者自行脑补；交稿前与术语自查一并检查全文（2026-07-21，用户反馈"航空靠事故报告"处的引用没看懂）
- 叙述测试场景/事故经过时，代词（如"它""该模型"）指代的对象必须明确，尤其当场景中同时出现多个实体（如 agent、被扮演的角色、人类操作者）时，需用具体名词替代代词或加以澄清，不能让读者猜"它"到底指谁（2026-07-21，用户看不懂"某高管把它关停"一句中"它"指代的是正在跑的 agent 还是高管本人）
- 描述法律判决/和解等结论时，若结论表面自相矛盾或违反直觉（如"囤积盗版书违法但用其训练构成合理使用"），必须在正文交代清楚支撑该区分的具体机制或事实依据（如涉案盗版副本与训练实际使用的副本是否为同一批次、区分点到底是"获取方式"还是"使用方式"等），不能只抛结论让读者自行合理化；同时须明确赔付/和解所覆盖的时间和行为范围（是仅追溯过去已发生的下载/训练行为，还是也约束或允许未来行为），不能笼统地说"赔的是 A 不是 B"（2026-07-21，用户看不懂 Anthropic 版权和解一文中"中央图书馆违法但训练合理使用"的区分逻辑，以及赔付具体买断的是哪些行为）
- 文中用博弈论/经济学逻辑解释某类主体的行为动机（如"公司为何选择和解而非上诉"）时，必须把关键决策变量讲清楚——尤其是"和解"与"败诉判例"在效果上的本质区别（如是否会为其他原告确立可援引的先例、判例效力是否会外溢到其他类似案件而不只是本案赔付），不能用"灭顶之灾"这类修辞代替具体的因果说明（2026-07-21，用户看不懂 Anthropic 版权和解一文中"和解买确定性"一段的论证逻辑，追问和解与判决败诉的区别到底在哪）
- 指代人群/主体时不用"做模型的""写书的""看行业的"这类口语化短语，改用正式名词（如"AI 研究者/大厂""作者""行业观测者"）；小标题、加粗术语等正式位置尤其要避免口语化（2026-07-21，用户指出"做模型的""写书的""看行业的"太口语，要求换成正式说法）
- 描述新型攻击手法/技术机制（如信息呈现位置、结构层面的操纵）时，仅给抽象定义不够，必须补一个具体、场景化的例子说明"怎么操作"导致了什么后果；使用"攻击"一词前须先核实机制的真实性质——是诱导模型做人为设定的恶意行为（如 jailbreak、窃取数据等 cybersecurity 场景），还是通过操纵冲突信息的权重/摆放让模型把错误信息当真实答案 pick up（hallucination 范畴，如多跳 RAG 中把旧信息误判为最新答案）；若属于后者，须在正文说清是"什么被操纵、如何导致误判"，不能笼统套用"攻击"一词或与蓄意作恶类攻击混为一谈（2026-07-21/22，用户先追问「显著性通道」换位置如何产生影响、没有攻击内容谈何攻击，后又指出该文实际讲的是冲突信息权重导致的 hallucination 问题而非 cybersecurity/jailbreak 式攻击）
- 提及作者本人从业经历时，只陈述客观事实（做过什么项目、什么职位），不添加自我评价/自我标榜性描述（如渲染"亲手摸索""深耕多年"之类突出个人专业深度的措辞）（2026-07-24，用户要求删除"我入行 Responsible AI 的第一个项目...是从那时开始亲手摸的"这段自我评价，只保留"做过 Nuance 这个项目"的事实陈述）
- 文末点睛句/收尾比喻若调用某个具体意象或典故（如某种许愿场景的具体后果）来做回扣，该意象必须已在正文中实际交代过；不能指望读者靠标题或主题自行脑补出一个从未讲过的具体故事，第一次抛出就放在收尾会让读者看不懂（2026-07-25，用户看不懂"精灵系数"一文结尾"不要收购咖啡园"这句话什么意思，该典故正文未曾交代）

## 事实核查点

- 文中援引具体产品/模型作为例证时（如"某模型权重已发布并广泛扩散到 Hugging Face、镜像、种子"），须逐一核实该具体表述本身的真实性——该模型是否真的已发布/开源，不能因为例子在直觉上说得通就直接采用；核实不了应换成能证实的例子，或在正文注明信息未经确认（2026-07-22，用户质疑"Kimi K3 权重已发布"这一表述是否属实）
- 文中涉及"谁最流行/谁被广泛部署"一类市场趋势判断（如"世界其他地区都在下载中国权重"）时，须用 Hugging Face 下载量、fine-tune 衍生模型数量等具体数据或可靠研究/报道核实实际情况，不能仅凭叙事逻辑顺畅或个人观感断言领先者是谁；这类判断往往隐含在论证逻辑里而非直接点名某个模型，尤其要主动挖出来核实（2026-07-22，用户提到身边团队微调最多的是千问，要求查证 Hugging Face/研究/报道确认当前部署最广的开源模型到底是哪家）
- 引用下载量/市场份额等可在平台上直接查证的数据时，不能只转引媒体对该数据的转述，尤其当所有转述来源集中于单一阵营/立场的媒体（如清一色中国官方或亲中媒体）；必须亲自到一手平台（如 Hugging Face 的模型页面、trending/ranking 榜单）核实原始数字，并优先补充独立于该阵营的信息源；仅有媒体转述、未能在平台上复核到的数字须在正文注明未直接核实（2026-07-22，用户质疑千问下载量领先的说法为何清一色引自新华社、SCMP 等中国媒体，要求直接查 Hugging Face 核实下载量排名）
