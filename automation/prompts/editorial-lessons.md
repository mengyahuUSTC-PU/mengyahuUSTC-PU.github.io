# 编辑教训（从用户历次反馈自动累积；所有写作/修改任务必读）

本文件由管线在每次用户反馈后自动更新：提炼可泛化的规则，合并去重。规则按主题分组。

## 交稿纪律

- frontmatter 的 title 和 description 一律用双引号包裹（英文冒号会炸 YAML，导致整站构建失败）（2026-07-19，快讯英文版标题含冒号导致部署挂掉）
- **绝不留 TODO/FIXME/待补注释交稿**。能当场验证的当场验证；确实无法验证的，并入「事实核查点」清单并写明验证指向。交稿前整体通读一遍，专查未完成项（2026-07-19，用户在 PR #6 抓到遗留 TODO）
- 用户的提问式反馈("这里是不是有问题？""有没有没做完的？")一律当作行动请求处理：查证并修复，而不是回答「是的有」或原样返回
- 安全相关论断需逐层核实事实基础：①描述 AI 安全「事故/事件」须核实是真实生产事故还是厂商/研究者的红队测试或评估实验，正文注明来源与事件性质，无法确认为真实事故不得称"事故"（2026-07-21）；②提及安全机制/防护效果需核实是否有对应场景的 benchmark 支撑，尤其区分单轮与多轮/长对话场景——现有安全研究多为单轮，机制若声称覆盖多轮却找不到对应研究，须在正文注明这一研究空白；同理，若论断涉及"多轮劝说/加长对话后拒绝被顶开"，应检索 multiturn jailbreak 成功率随对话轮次变化的论文数据，找不到须注明空白而非默认成立（2026-07-21；2026-07-29，用户追问"别把模型拒绝当能力天花板"一条判断有无 multiturn 相关论文数据支撑）；③引用研究支撑某论断时须核实该研究实际测量的构念（construct）与论断性质一致，如论断讲"安全约束力衰减"就不能引用测"任务成功率"（能力）的论文，需换成真正测安全行为（如 jailbreak 成功率）的研究（2026-07-21）
- 文中对事件/做法使用"罕见""首次"等程度或频率判断词，或提出自造的概念/框架/指标暗示其新颖性时，须能给出可验证依据——横向对比同类案例、检索相关领域是否已有对应成熟研究方向；若已有相关研究，须在正文说清新提出的东西与既有研究的关系及具体新意所在，不得自称首创；无法证实则删除该修饰词或改写为客观中性表述（2026-07-21，"罕见公开"、"精灵系数"两例）
- 文中声称某做法具备合法性/可复制性时，必须核实其适用范围——是仅针对本案涉事公司、涉事内容类型成立，还是可泛化为通用规则；来源未明确回答范围时，须在正文注明这是尚未确认/存在争议的推论（2026-07-21，"买书扫描训练合法"是否对所有公司、所有版权内容类型都成立）
- 针对 inline comment 逐条修改后，正文容易残留"回答式"语气；逐条改完后必须整体通读一遍，把问答腔改写为自然叙事语气，同时检查全文行文顺畅、故事结构完整，不能只满足单条评论的字面要求（2026-07-21；2026-07-26）

## 内容对称

- 中英两版内容必须保持对称：既包括段落文字对应，也包括小节结构完整（翻译/改写不得省略原文版本中的实质性小节，如对比分析、实际影响案例）；单边修改后要主动提示用户另一版是否同步（2026-07-19）

## 信息源

- 不收录标题党/二手聚合类媒体的转述（中国公司动态走官方渠道+HN/TechCrunch，宁缺毋滥），也不收录个人博客的评论/类比/观点分析文章（即便作者有资历、论点有价值）——这类内容如确有价值，应转化为专题文章的论据或背景引用，而非当作快讯条目收录（2026-07-19；2026-07-26，Mesosphere 联合创始人"开源权重 Kubernetes 时刻"一文被判定为类比评论而非新闻）
- 报道范围不能偏科：新品/新闻不能只盯中国厂商，需同步纳入美欧 AI 新闻与监管动态、消费级平台的 AI 产品与政策；技术专题盘点各家工作时也不能漏掉大厂（2026-07-20）
- 快讯条目收录前须能说清该事件与「AI 前沿趋势」的直接关联，不能仅因涉及 AI 技术就默认够格；若事件缺少动机说明需如实指出信息空白并自问是否具备行业信号/先例意义；同时须自问该条目对目标读者（AI 从业者）是否有实际参考价值，仅报道"有意思的社会现象"而给不出从业者启示的应删除或谨慎收录；专题文章引入尚无成熟共识的新概念时同理，须明确交代对 user/builder 的具体应用方向或如实说明"目前只是值得关注的新动向"；快讯收录学术论文时须自问其实际贡献——是否只是系统性验证/量化了业内已知常识，给不出新方法/新发现须点明贡献在于系统性实证本身（2026-07-22；2026-07-26；2026-07-28；2026-07-29，越狱防御三类方法评测论文是否只是重复已知常识）
- 文章主题若与用户本人此前在个人网站发表过的相关文章重合，应主动提及并附上该文章链接（2026-07-29，密码分析一文的双重用途讨论与用户个人网站近期文章相关）

## 呈现

- tags 一律英文小写 kebab-case，两语言版本共用；英文界面出现中文是硬伤，中文界面出现英文可接受（2026-07-19）
- 社交分发内容要短，只放最强 hook 和一两个冲击点、全文引流到博客，且必须留信息缺口+动词开头的明确 CTA（帖子把话说完读者就无需点击）；**X 永远只发单条 post（≤270 字符），绝不做 thread**；LinkedIn ≤150 词（2026-07-19）
- 快讯的标题链接必须是一手来源（官方公告/arXiv/原始披露），聚合博主的转述链接一律不出现；官方只在 X/社交帐号公告、无官网新闻页时，引 X 原帖为一手来源并在正文注明「官方仅在 X 公告」（2026-07-19）
- 快讯必须条目式，每条标题挂原文链接；重要事件不得埋在段落里（2026-07-18）
- 分节标题（尤其并列结构）必须与实际内容的分量和逻辑对应；若某几项内容单薄或不成体系，不能为凑并列结构勉强安上标题，应重新划定 scope、改写标题或充实内容（2026-07-21）

## 语言与表达

- 避免"AI 味"空洞升华式短语和刻意对仗的排比修辞，改用直白具体的说法陈述事实；**「能带走什么/能带走的判断」（takeaway 直译）全面禁用**，总结段标题改用「核心启示」「关键结论」或结合内容的具体说法；同类翻译腔比喻（如把"an honest cliffhanger"直译成"诚实的悬念"）也偏生硬，交稿前需专门检查是否残留这类不自然的翻译腔短语，而不仅仅是排查"带走"一词本身（2026-07-19；2026-07-24；2026-07-26；2026-07-29，"诚实的悬念"翻译生硬，且"读者带走的一句"再次出现已被禁用的"带走"）
- 不要植入缺乏普遍共识支持的价值判断/因果论断，无充分论据应直接删除；提出"把审核/判定从某一层移到另一层"一类替代方案时，须验证新方案是否真正解决了原问题而非只是转移问题，并如实评估新增成本；讨论内容审核/分类类系统（尤其判定边界主观的内容）时，须承认标注者间分歧、FP/FN 权衡、语境因素、不同用户群体接受度不同导致无法有 universal 标准；给不出化解方案时须在结论处如实承认这是难以完全解决的本质问题，不能假装"已解决"（2026-07-19；2026-07-26）
- 文中引入专业/抽象术语、机构名/缩写、跨行业类比、抽象机制/流程说法时，必须在正文顺带给出简明解释和/或具体场景化例子，不能预设读者已理解、也不能让标题提了正文不展开；带主观判断色彩的标准（如"合理人"）需说明定义并如实指出其主观性；描述模型自身具体行为/表达时需给出模型实际输出的具体例句而非只用抽象归纳；描述新型攻击手法/技术机制时需给出具体场景化例子说明"怎么操作导致了什么后果"，并核实"攻击"一词是否用词准确（是蓄意作恶式攻击，还是信息权重导致的 hallucination）；描述技术性漏洞/破解结果（如密钥恢复代价降低、搜索空间减半）时，除了解释术语本身，还必须说清对现实世界的具体含义——如是否意味着攻击者可以更快破解真实系统、影响到谁——不能止步于定义名词让读者自己脑补后果；文中把公开信/政策诉求提炼为简短口号式说法（如"能停""调速能力"）时，须回到信中或原始材料核实该能力具体由哪些技术/治理机制构成（如可验证的算力监测、核查协议、评估标准等），不能止步于抽象口号让读者自行脑补其具体内容（2026-07-21；2026-07-25；2026-07-26；2026-07-28；2026-07-29，"HAWK""NIST"未解释看不懂；密钥恢复代价减半是否意味着坏人能用来更快破解密码；2026-07-30，"Pacing the Frontier"联署信中"能停"的能力未说清具体指什么）
- 引用第三方构建的评分/指数或按某指标分组/分档（且该分组是核心论据）时，须交代评分是谁打的、依据什么方法，并给出高档和低档各自的具体例子帮助读者建立直观认识，不能只呈现分数/档位标签（2026-07-26）
- 叙述测试场景/事故经过时，代词（如"它""该模型"）指代的对象必须明确，尤其当同时出现多个实体（agent、被扮演角色、人类操作者）时需用具体名词替代或加以澄清（2026-07-21）
- 描述法律判决/商业决策结论（尤其表面自相矛盾、违反直觉，或用博弈论/经济学逻辑解释动机）时，必须在正文交代支撑该结论的具体机制或关键决策变量（如区分点是"获取方式"还是"使用方式"、和解与败诉判例在先例效力上的本质区别），不能只抛结论或用"灭顶之灾"之类修辞代替具体说明，也不能笼统地说"赔的是 A 不是 B"而不交代覆盖的时间/行为范围（2026-07-21）
- 指代人群/主体时不用"做模型的""写书的""看行业的"这类口语化短语，改用正式名词（如"AI 研究者/大厂""作者""行业观测者"），小标题、加粗术语等正式位置尤其要避免（2026-07-21）
- 提及作者本人从业经历时，只陈述客观事实，不添加自我评价/自我标榜性描述；但文章主题涉及内容审核时，可用第一人称点出作者本职做内容审核、切身体会"两边不讨好"的处境作为支撑论点的事实陈述，不算自我标榜（[[user-does-content-moderation]]；2026-07-24；2026-07-26）
- 文末点睛句/收尾比喻若调用某个具体意象或典故来做回扣，该意象必须已在正文中实际交代过，不能指望读者靠标题或主题自行脑补一个从未讲过的故事（2026-07-25）

## 事实核查点

- 文中援引具体产品/模型作为例证时，须逐一核实该具体表述本身的真实性（如是否真已发布/开源），核实不了应换成能证实的例子或注明信息未经确认（2026-07-22）
- 涉及"谁最流行/谁被广泛部署"一类市场趋势判断时，须用 Hugging Face 下载量等一手平台数据核实，不能仅凭叙事逻辑或转述断言，尤其避免转述来源集中于单一阵营/立场的媒体；数据一旦已能用一手信源独立坐实，应删除同一论断的二手媒体转述陪衬，避免让读者误以为论断依赖该阵营媒体（2026-07-22）
- 报道政策/官员表态类事件时，即便正文未用"首次"字样，也须主动检索该表态是否为旧事重提，并在正文注明是新进展还是延续既有立场（2026-07-22）
- 分析制裁/限制类政策的代价时，若已论及对目标方的代价，需一并核实是否对己方也构成代价/反噬；引用反噬案例前必须核实官方一手信源是否真实支持该叙事，不支持则不得写入（2026-07-22）
- 用户已明确否决/要求删除的具体条目或说法，不得在后续文章中原样再次出现；写作前应对照近期反馈记录（2026-07-23）
- 将某公司计划类比/对照到其他公司历史先例时，必须实际调研该先例公司具体做了什么、是否有相关诉讼及结果，逐项梳理与本文场景的相同点、不同点，并提炼可直接迁移的经验教训，不能只做浮于表面的泛泛类比（2026-07-24，Nuance 先例调研）
- 描述算法/技术机制的具体运作步骤（如推测解码的"起草-验收"流程）时，须核实一手论文对该步骤的准确定义，不能凭直觉或常见类比代入；若声称某步骤更快，须点明真正的计算原理（如并行前向计算 vs 依次生成）；模型输出本身是概率采样、同一输入结果可能不同，描述接受/拒绝判定时须讲清具体比对方式（贪心匹配还是按概率比值的拒绝采样），不能默认存在笼统的"容差"（2026-07-28）
- 引用统计数字/比例时，须说清统计的是训练阶段还是部署后输出、分子分母具体指代什么；分母若是"互动/对话"，还须说清抽样方式——是自然抽取所有类型任务，还是专门筛选情感相关 prompt，因为混入大量无情绪场景任务会稀释比例；说明统计对象是"模型输出"时不能因此暗示与输入无关，需把"统计输出而非训练数据"和"输出是否受当批输入类型影响"分开讲清楚（2026-07-28）
